# 黑鑽選股系統 — Zeabur 部署包

架構與您現有的加密貨幣篩選器一致：**FastAPI 後端 + React 前端**，
用單一 Dockerfile 打包成一個服務（前端 build 後由後端直接 serve），
方便在 Zeabur 上以單一服務部署。

```
bd-app/
├── Dockerfile              # 多階段build：先build前端，再放進Python image
├── .dockerignore
├── .env.template
├── backend/
│   ├── main.py              # FastAPI：API + 靜態檔serve
│   ├── engine.py            # 黑鑽SOP 6道濾網篩選引擎
│   ├── storage.py           # JSON檔案儲存（settings/candidates/holdings）
│   └── requirements.txt
└── frontend/
    ├── src/App.jsx           # 主要UI（4個分頁：選股/計算/追蹤/SOP）
    ├── src/main.jsx
    ├── index.html
    ├── package.json
    └── vite.config.js
```

## 本機測試（部署前建議先跑一次）

```bash
# 1. 打包前端
cd frontend
npm install
npm run build

# 2. 把build結果放進後端的static目錄
cp -r dist ../backend/static

# 3. 啟動後端（會同時serve API與前端頁面）
cd ../backend
pip install -r requirements.txt --break-system-packages
uvicorn main:app --port 8000

# 4. 瀏覽器開 http://localhost:8000
```

這個流程我已經在沙盒環境完整測試過一輪（API的CRUD、靜態檔serve、SPA路由fallback都正常）。

## 部署到 Zeabur

1. 把整個 `bd-app/` 目錄推到一個 GitHub repo（或您現有專案的子目錄）。
2. 在 Zeabur 建立新服務，選擇這個 repo，Zeabur 會自動偵測到根目錄的 `Dockerfile` 並用它建置。
3. **重要：掛載 Volume 才能保留資料**
   - 這個服務用本機 JSON 檔存 `settings.json` / `candidates.json` / `holdings.json`，
     預設寫在容器內的 `./data`，**容器重啟會被清空**。
   - 到 Zeabur 服務設定 → Volume，掛載一個路徑，例如掛到 `/data`。
   - 然後在環境變數加上 `DATA_DIR=/data`。
4. 其餘環境變數可參考 `.env.template`：
   - `PORT`：Zeabur 會自動注入，不用自己設定。
   - `CORS_ORIGINS`：只有前後端分開部署在不同網域時才需要設定成該網域；
     這個包預設前後端同源部署，可以不用管。
5. 部署完成後，直接打開 Zeabur 給的網址即可看到「選股清單／停損停利計算／持股追蹤／SOP速查」四個分頁。

## 關於「執行篩選」功能

前端「選股清單」頁提供三種取得候選股的方式：

1. **從後端跑一次篩選（少量自選股）**：輸入代碼清單，呼叫
   `POST /api/screen/run`（`source: "symbols"`）觸發背景執行緒跑濾網邏輯，
   前端每 1.5 秒輪詢 `GET /api/screen/status` 顯示進度。適合你已經在關注的股票。

2. **全市場掃描（網頁按鈕）**：點「開始全市場掃描」會呼叫
   `POST /api/scan/full-market/run`，伺服器背景執行緒抓取 NASDAQ + NYSE
   完整上市清單（數千檔）並套用預設濾網參數逐檔檢查，過程中可離開頁面，
   回來會自動看到最新結果與已通過檔數。**這是長時間工作（可能數十分鐘），
   請留意 Zeabur 服務是否有請求逾時或休眠設定**，若容器會因為沒有前台流量
   自動休眠，長時間背景任務可能被中斷。

3. **自動排程**：同一個面板可以設定「每隔幾小時自動掃描一次」並啟用，
   設定會存進 `schedule.json`，用 APScheduler 在伺服器內用
   `IntervalTrigger` 定期觸發全市場掃描，掃描結果直接覆蓋 `candidates.json`。
   面板會顯示「上次掃描時間／通過檔數」與「下次排程時間」。
   注意：
   - 排程只在伺服器程序持續運行時才會觸發，若服務重啟，會依照儲存設定
     重新註冊定期任務。
   - 若 Zeabur 該服務有「無流量自動休眠」的設定，排程可能因為沒有流量
     而不會準時觸發；建議先在 Zeabur 服務設定確認是否有休眠機制，
     若有，需要關閉或改用外部 cron 定期打 `/api/scan/full-market/run`
     喚醒服務。
   - 全市場掃描與自選股篩選共用同一個背景工作位，同時間只能跑一個，
     若排程觸發時剛好有其他篩選在跑，會自動略過本次排程等下一輪。

## 切分頁 / 重新整理不會中斷掃描

掃描工作的進度輪詢邏輯放在最上層（App 元件），不是放在「選股清單」這個分頁裡，
所以切換到「持股追蹤」「SOP速查」等其他分頁時，掃描仍會在伺服器背景繼續跑，
回到「選股清單」會自動接回目前進度。就算重新整理整個網頁，一開頁也會先跟後端
確認目前有沒有工作正在執行（`GET /api/screen/status`），有的話會自動接上輪詢，
不會誤以為沒在跑而重新觸發一次掃描。

## 個股快取，避免重複檢查浪費時間

後端會把每檔股票的檢查結果連同「檢查時間」存進 `symbol_cache.json`：

- 掃描時，如果某檔股票是在有效期內（預設 24 小時，環境變數
  `CACHE_FRESHNESS_HOURS` 可調）已經檢查過，會直接沿用快取結果，
  不會再對 Yahoo Finance 發送請求，也省下等待時間。
- 掃描過程中每處理 25 檔會把快取存檔一次；就算掃到一半服務被中斷
  （例如 Zeabur 重啟），下次重新觸發掃描時，已經檢查過的股票會直接命中快取，
  等於是從中斷的地方接續下去，而不是整個從頭來過。
- 「選股清單」頁的「全市場掃描」面板下方有「個股快取」區塊，
  顯示目前已快取幾檔股票，也可以手動「清除快取」強制全部重新檢查
  （例如濾網參數調整後，想確保用最新資料重新評估）。
- 進度列會顯示「快取 X / 新查 Y」，可以看出這次掃描實際打了幾次 Yahoo Finance、
  省下了幾次。

## 個股線圖

「選股清單」的候選股表格點代碼或「看線圖」，「持股追蹤」每筆持股旁的「看線圖」，
都會跳出近 5 年週K走勢圖（`GET /api/chart/{symbol}`，資料來源 Yahoo Finance），
方便對照 SOP 要求的人工判斷：低位盤整時間 ≥ 2 年、是否剛突破盤整起漲。
候選股會標出現價／52週高低參考線；持股會標出進場價／停損價參考線。
同一檔股票 6 小時內重複開圖會直接用伺服器端記憶體快取，不會每次都重打 Yahoo Finance。

## 全市場掃描完成通知

全市場掃描（手動按鈕或每週排程）跑完後，會透過 Telegram 通知候選股數量與型態分數最高的
幾檔，提醒使用者進來「選股清單」做人工複核，跟超速大盤共用同一組 Telegram Bot 設定
（在「超速大盤」分頁設定）。

## 型態分數（輔助判斷，非取代人工判斷）

篩選工作在 6 道濾網跑完之後，會對「通過濾網的候選股」（通常只有幾檔到幾十檔，
不會對整個母體做，避免拖慢全市場掃描）額外抓一次5年週K，計算 0~100 的型態分數：

- **基期夠緊**：近2年（排除最近3個月）價格區間 `(最高-最低)/最低` 越小分數越高
- **基期夠平**：同一段期間頭尾價格變化越接近 0% 分數越高，避免把「持續緩漲」誤判成「盤整蓄積」
- **確認突破**：最近3個月的高點要真的站上基期高點才算數
- **突破幅度合理**：站上高點後漲太多（已經噴出一段）會被扣分，避免追高

突破相關的分數會依「基期品質」（緊+平）打折——如果基期本來就不合格（例如其實是持續上漲，
不是真正橫盤），就算價格創新高也不會給高分，避免把一般的上升趨勢股誤判成典型的黑鑽起漲型態。

**這是排序輔助工具，不是取代人工判斷**：無法判斷除權息調整是否正確、有沒有假突破、
是不是剛IPO資料不足、有沒有重大事件（併購、財報意外等）在扭曲價格型態。
候選股清單預設依型態分數排序，建議優先看分數高的幾檔，點「看線圖」肉眼複核後再決定是否進場。

## 超速大盤策略（自動化，取代 Excel 手動維護）

「超速大盤」分頁把原本要手動維護的 Excel 紀錄表整個自動化。規則（已對照使用者實際
Excel公式核對過，逐項數字都能重現）：

1. 每月一個檢查日，抓基準ETF（預設 QQQ）當日調整後收盤價。
2. 1個月／3個月／6個月績效 = 這次價格 vs「前1次／前3次／前6次讀值」
   （是讀值次數，不是嚴格日曆月，與原Excel公式一致）。
3. 綜合動能指標 = 三者中有算出來的那幾個的平均值。
4. 指標 ≥ 0 → 持有／進場交易標的（預設 QLD）；指標 < 0 → 全數出場轉現金。
5. 訊號在讀值當天判斷；**實際換倉需要你自己操作完之後回來確認**，系統才會更新
   股數/現金——不會自動假設交易已經完成（詳見下方「確認執行流程」）。

使用者附件Excel最後一筆讀值（2026-08-17）動能指標為正值卻記錄「持有現金」，
已向使用者確認為當時的主觀override（非規則遺漏），系統維持照規則字面實作，
並提供「手動調整目前部位」功能因應未來類似的主觀override情況（見下方說明）。

### 使用方式

1. 到「超速大盤」分頁，「進階」區塊已經預填好使用者附件Excel裡的16筆真實歷史讀值
   與目前部位（持有現金 $730，本金 $580），按「匯入」即可一鍵接上舊資料。
2. 在「設定」填基準ETF／交易標的／本金／每月檢查日，勾選「啟用自動排程」。
3. 若要 Telegram 通知，填入 Bot Token 與 Chat ID、勾選啟用，按「傳送測試訊息」確認能收到。
4. 之後伺服器每天會自動判斷（`POST /api/momentum/check-now` 背後邏輯，UTC 21:30 跑一次）：
   - 有「待確認換倉」還沒確認 → 每天提醒一次，不會自動做任何事。
   - 沒有待確認事項、且輪到本月檢查日 → 抓基準ETF收盤價、算動能指標、決定要不要換倉，
     需要換倉才會發 Telegram 通知（不需要換倉的月份不會吵你）。
5. 也可以隨時按「立即檢查一次」手動觸發，方便測試或補跑漏掉的月份。
6. 如果哪個月主觀判斷要偏離系統建議（像使用者附件Excel最後一筆那樣自行出場），
   用「手動調整目前部位」面板直接更新股數/現金/部位，不用整批重新匯入；
   會順便清掉任何待執行的自動換倉，並可附上備註記錄override原因。
   歷史紀錄表每一列的「備註」欄位也可以隨時點擊補充說明。

### 確認執行流程（避免「忘記操作」跟系統紀錄對不起來）

早期版本一偵測到訊號，就會在隔天自動依開盤價把換倉記錄下去、更新股數/現金——
但這樣如果使用者忘記在券商實際下單，系統還是會自顧自地記錄成「已完成買進」，
導致系統紀錄的部位跟真實帳戶完全對不起來（曾實際發生：系統通知「已完成買進 QLD」，
但使用者根本沒有下單）。

現在改成**一定要人工確認**才會更新股數/現金：

1. **訊號觸發時**：發 Telegram 通知，說明建議動作、建議操作日，並提醒「請操作完後回來
   確認執行結果，在你確認之前系統不會更新股數/現金」。此時 `state.pending_trade` 只是
   記錄「有一筆訊號待確認」，`shares`/`cash` 完全不變。
2. **每天排程跑的時候**，只要這筆訊號還沒被確認，就會再發一次提醒（附上當天的參考價），
   而且**不會**去檢查是否輪到下個月的讀值判斷，避免疊加更多待確認事項搞混。
3. **使用者回到「超速大盤」分頁**，會看到醒目的「⚠ 需要你確認」面板：
   - 如果已經照建議操作了 → 填入實際成交日期與成交價，按「確認已執行」，
     系統才會真正更新股數/現金、回填對應的歷史紀錄列（換倉日/換倉價/資產總額/累計報酬）。
   - 如果決定不跟這次訊號（忘記操作、或主觀判斷不跟）→ 按「跳過這次訊號」，
     部位維持原狀，待確認狀態清除，不會再重複提醒這一筆。
4. 對應的 API 是 `POST /api/momentum/confirm-trade`，body 為
   `{"executed": true, "execution_date": "...", "execution_price": ...}` 或
   `{"executed": false}`。

這樣不管使用者多久才回來確認，系統紀錄的股數/現金永遠反映「使用者親口回報的真實狀況」，
不會自己憑空生出一筆從未發生的交易。

### 关于 Telegram Bot 設定

跟 @BotFather 對話建立一個新 Bot，取得 Bot Token 貼到「超速大盤」分頁的設定裡；
接著傳一則訊息（例如 `/start`）給你的 Bot；回到頁面按「自動取得 Chat ID」，
後端會呼叫 Telegram 的 `getUpdates` 自動抓出 Chat ID 幫你填好，不用自己組API網址查。
如果這個 Bot 之前設定過 webhook 導致 `getUpdates` 沒反應，後端會自動先移除 webhook 再重試一次。
如果按了還是抓不到，代表 Telegram 那邊真的還沒收到你傳的訊息，先確認訊息有送出去再重試。

「傳送測試訊息」會直接用畫面上目前的 Token / Chat ID 測試，不用先按「儲存設定」，
也不受「啟用 Telegram 通知」開關影響（測試本來就是為了在正式啟用前先確認能不能收到）。
但正式的排程通知（超速大盤訊號變化、全市場掃描完成）需要勾選「啟用 Telegram 通知」
並按「儲存設定」才會真的發送——這兩者是分開的路徑，這也是為什麼原本有人會遇到
「勾了啟用但測試還是說沒開啟」的情況：測試讀到的是「已存檔」的設定，勾選後如果沒按儲存，
後端當然還是舊的值，現在已經改成測試不依賴已存檔設定。

## 排程遇到美股假日的處理

超速大盤的每月檢查日若剛好遇到平日休市的美股假日（感恩節、聖誕節等，不只是週末），
系統會直接向 Yahoo Finance 確認「這天真的有開盤嗎」，沒開盤就跳過、明天排程再檢查一次，
一直到真正有開盤的那天才會執行讀值判斷，不會誤用假日前的舊收盤價。
換倉執行（隔一交易日開盤價）本來就是往後找最近有資料的交易日，同樣不受假日影響。

4. **貼上 candidates.json 匯入**：如果想在本機先跑好再匯入（例如想調整
   濾網參數做離線測試），可以：
   ```bash
   python backend/engine.py --fetch-nasdaq --out candidates.json
   ```
   跑完把 JSON 內容貼到前端「貼上 candidates.json 匯入」欄位即可。

## 黑鑽飆股策略 — 持股追蹤（取代原本的 Excel 紀錄表）

「持股追蹤」分頁已經整個換成比照使用者「黑鑽飆股策略紀錄表」Excel重建的完整版
（欄位、公式都對照過真實試算表數字，逐項驗證一致）：

**風險與部位計算**（對應 Excel 的「風險金額&應買股數計算」表）：
- 策略本金 × 風險比例 = 風險金額
- 應買股數 = round(風險金額 / (進場價 − 止損線))
- 新增持股時會即時顯示 -20%/-25% 參考價（幫助決定止損線要設在哪個支撐位）與建議應買股數

**進出場紀錄**（對應「進出場紀錄表」）：
- 停利線 = 進場價 × 1.2（自動算）
- 最多4次分批出場記錄（原因/價格/股數/日期），原因是跟 Excel 一模一樣的7選項下拉：
  收盤價跌破止損線、1個月/2個月未達停利線、盤中跌破SMA20/EMA60/EMA120、漲達停利線後跌回進場價
- 未出清股數、買入/賣出金額、持有市值、未實現/已實現損益、損益比例、未實現+已實現：
  全部自動計算，公式跟 Excel 完全一致
- 帳戶總覽（策略本金/總買入/總賣出/總持有市值/總未實現損益/帳上流動資金/帳上淨值/整體報酬率）
  對應 Excel 最上方那排彙總欄位

**自動比對出場規則 + Telegram 通知**：
- 「持股追蹤」設定裡開啟「啟用自動排程」後，伺服器每天會對所有持有中的部位：
  抓最新收盤價、算 SMA20/EMA60/EMA120，依照 7 條規則的優先順序逐一比對
  （止損線最優先且會持續提醒；1個月/2個月未達停利線；曾觸及停利線後改用均線分批出場）
- 符合規則時發 Telegram 通知（跟超速大盤共用同一組 Bot 設定），內容包含觸發原因、
  建議出場股數、現價、進場價、止損線
- 同一個關卡（例如 SMA20 那一次）只會通知一次，不會每天重複洗版；
  止損線是例外——只要還沒平倉、現價持續在止損線之下，每天都會再提醒，避免忘記處理
- 系統只負責提醒，**不會自動下單**：收到通知後，實際出場價格/股數/日期仍要自己執行後
  在頁面上按「記錄出場」回填，這樣未出清股數、損益等數字才會跟著更新，完全比照原本
  Excel「人工填入出場欄位」的方式，只是不用再手動查K線、算指標
- 也可以隨時按「立即檢查所有持股」手動觸發，不用等排程時間到

## Docker 建置速度優化

- 前端安裝改用 `npm ci`（搭配 `package-lock.json`）取代 `npm install`：
  結果是確定性的、通常也比較快，同時保留原本「先複製依賴清單、安裝完再複製原始碼」
  的分層順序，讓 Docker layer cache 在依賴沒變動時可以重複使用。
- 後端 `requirements.txt` 改成釘死版本號（原本是 `>=` 範圍），減少 pip 每次都要重新
  解析相依關係圖的時間，也讓每次部署裝到的版本一致、行為可預期。
- 如果 Zeabur 的建置環境本身不會在多次部署之間保留 Docker layer cache，
  上面兩項優化幫助有限（因為每次都是全新安裝）；這種情況下，
  唯一能再壓縮的空間是進一步精簡依賴或改用建置更快的 base image，
  目前用的 `python:3.11-slim` 已經是常見的效能/相容性折衷。

## 超速大盤：追加/提領本金

「超速大盤」分頁新增「追加 / 提領本金」面板，對應「空手期間想加碼、下次進場放大部位」
的需求：

- 送出金額（正數＝追加、負數＝提領）後，本金基準（`settings.initial_capital`）與
  現金（`state.cash`）會同步調整
- **報酬率計算方式**：本金調整之後的讀值會用新的本金基準計算「整體帳戶報酬率」，
  避免把新存入的錢也算成獲利、或被稀釋掉；調整之前已經算好的歷史紀錄維持原樣，
  不會回頭改寫。這是簡化處理，不是嚴謹的資金加權報酬率（time-weighted return），
  但對個人記錄用途足夠
- 每筆調整都會記錄下來（金額、日期、備註），方便回頭查什麼時候為什麼調整過本金
- 建議在「持有現金」的狀態下調整，避免跟持股中的部位混在一起——這個限制目前是
  UI 文字提醒，後端沒有強制擋

## 績效比較圖：策略 vs 大盤

「超速大盤」分頁新增走勢圖，把策略的累積報酬跟基準ETF（預設QQQ）單純買進持有的
累積報酬畫在同一張圖上，並列出「超額報酬」（策略－大盤）：

- 策略的累積報酬用「現值估算」（`mtm_*` 欄位）：每次讀值當下，不管有沒有觸發換倉，
  都會用當時實際持有的股數/現金 × 交易標的當時價格概算市值，這樣走勢圖才不會因為
  「這個月沒換倉」就整月缺資料。這跟 `total_value`/`cumulative_return`
  （只在使用者確認實際執行結果後才會寫入的「已確認真實帳務」）是分開的兩組數字。
- 大盤的累積報酬是單純的買進持有對照組，用歷史紀錄裡本來就有的基準ETF價格算，
  不需要額外資料來源。
- 至少要有2筆讀值紀錄才畫得出走勢，資料不足時會顯示提示文字。

### 匯入真實歷史換倉紀錄（優先於回測估算）

原本的Excel紀錄表其實每一列都有真實記錄當時的換倉狀態（隔天日期、QLD開盤價、
持有股數、持有現金），不是只有動能指標。匯入功能已經改成表格編輯器（不用再手key
JSON），欄位對應：讀值日期、基準價(QQQ)、換倉日期、換倉價(QLD)、股數、現金——
後四欄如果原本有真實記錄，直接照Excel填入即可，系統會用這些真實數字算出
每個時間點的市值與累積報酬，比回測估算準確（因為那是真的發生過的事，不是模擬的）。

如果某幾列原本沒有真實記錄（例如剛開始還沒有足夠歷史資料判斷動能、還沒進場的那幾個月），
後四欄留空即可，系統會在有網路資料的情況下自動用回測估算補上那幾列的缺口，
但只會補「真的沒有真實資料」的部分，不會覆蓋你填的真實數字。

表格下方也有「改用貼上整批取代」的進階選項，如果想一次貼多筆可以用逗號或Tab分隔、
每行一筆的格式貼上（`日期,基準價,換倉日期,換倉價,股數,現金`，後四欄可留空）。

### 舊資料的回測回填（沒有真實換倉紀錄時的次選方案）

如果沒有真實的歷史換倉資料可以匯入，系統會用「回測回填」頂上：抓交易標的
（預設QLD）的歷史價格，模擬「如果從第一筆開始機械式照規則執行」，
算出每個時間點的市值估算，讓績效走勢圖不會因為缺資料而只剩大盤那條線孤零零地顯示。

⚠ 這是回測估算，反映的是「演算法建議動作」的理論績效，不是使用者當時
實際的真實操作（如果曾經手動override過，這裡不會反映那次的真實選擇）——
所以只要有真實紀錄，優先用真實紀錄匯入，回測估算只是沒有真實資料時的備案。

如果之前已經用回測估算匯入過、後來想換成真實資料，直接重新匯入覆蓋即可；
如果只是想補齊某幾列缺資料而不想整批重來，績效比較圖偵測到有讀值缺資料時
會自動跳出「回填歷史績效資料」按鈕，按一下就會呼叫 `POST /api/momentum/backfill-mtm`
只補上最前面缺資料的區塊，已經有真實追蹤紀錄的部分完全不會被覆蓋或更動。

## 「取得收盤價失敗」的常見原因與處理

如果在「超速大盤」「黑鑽飆股持股」按「立即檢查」時遇到「取得 QQQ（或其他股票）
收盤價失敗，請稍後再試」，通常不是程式邏輯的問題，而是 **Yahoo Finance 那邊暫時性
擋掉了請求**——這是 yfinance 這個套件生態系統很常見的狀況：Yahoo 偶爾會對雲端主機
的IP做更嚴格的限流（HTTP 429）或調整驗證機制，過一段時間通常會恢復正常。

已經做了兩層處理：
1. `yfinance` 套件版本從 `0.2.40` 更新到 `1.7.0`（原本的版本已經是一年多前的舊版，
   跟不上 Yahoo 端的變動）。已確認新版的 `Ticker.history()` / `Ticker.info` 介面
   跟原本程式碼完全相容，不用改任何呼叫方式。
2. 所有跟 Yahoo Finance 要資料的地方（超速大盤讀值、持股規則檢查、個股線圖、
   黑鑽選股篩選）都加上重試機制：失敗後間隔遞增重試最多3次，才會真的回報失敗，
   提高單次操作在遇到暫時性限流時仍然成功的機率。

如果重試3次後還是失敗，代表當下 Yahoo 那邊的問題比較持續，這時候「請稍後再試」
就是字面上的意思——過幾分鐘到幾小時再試通常會恢復。如果長時間（例如超過一天）
持續失敗，才需要懷疑是不是 Yahoo 又調整了什麼、需要進一步更新 yfinance 版本。

## 已知限制

- yfinance 抓取的是免費公開資料，準確度與更新頻率不如 ZACKS / Portfolio123，
  僅供初篩參考，最終仍需人工複核（5年線圖型態、AMEX排除等，SOP速查頁都有列）。
- 目前資料儲存是單檔 JSON，非多人協作/多帳號設計，適合個人使用。
